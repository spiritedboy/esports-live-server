## Phase 0：环境与工程边界（2026-10-29）

本阶段只实现日志和环境检测。当前没有输入流、AVPacket/AVFrame 分配、
编码线程、媒体队列或网络连接。以下媒体知识是后续阶段的理解准备，不代表已实现。

### FFmpeg C API 与模块关系

main 通过 extern "C" 引入 FFmpeg 头文件，使链接使用 C 符号。
av_version_info 返回总体版本；avformat_version、avcodec_version、
avutil_version、avfilter_version、swresample_version、swscale_version
返回实际运行库的整数版本。高位是 major，后两部分分别为 minor/micro，
通过 AV_VERSION_MAJOR/MINOR/MICRO 拆分；不能把 FFmpeg 6.1 与 libavcodec 60
当作相同编号体系。

头文件宏表示编译时依赖，函数返回值表示实际加载依赖，两者都输出才容易定位混装。
主版本比较是最小检查，不能替代动态链接或功能测试。编译时 pkg-config 找到库
也不能证明运行时加载的是同一份库。

avcodec_find_encoder_by_name、avcodec_find_encoder 查询编码器；
av_guess_format 查询 FLV 封装器；avio_enum_protocols 的 output=1 枚举输出协议。
这些描述符和名称由 FFmpeg 管理，调用者不释放。
未使用过时的全局注册接口，未创建网络连接，因此不调用网络初始化/清理。

基础库 esports_common 仅依赖标准库和线程支持；ffmpeg_env_check 额外链接 FFmpeg；
logger_test 仅链接基础库。这样后续媒体模块可以复用日志而不扩大其依赖。

### AVPacket 与 AVFrame 的生命周期和所有权

AVPacket 通常携带压缩数据（如 H.264 访问单元或 AAC 数据），AVFrame 携带解码后的
视频像素或音频采样及其属性。它们都是“描述结构 + 数据缓冲引用”，不能用普通
结构体浅拷贝表达独立所有权。

后续会用 av_packet_alloc/av_frame_alloc 创建描述结构，用 av_packet_free/
av_frame_free 最终释放。unref 释放当前持有的数据引用并重置描述字段，但保留
可复用的结构。ref 创建新的缓冲引用，move_ref 转移引用并清空源对象；跨线程传递
时必须明确唯一所有者或引用计数关系，不能把循环复用的裸指针直接放入队列。
共享缓冲后若要修改数据，需要遵守可写性约束，不能假定引用计数等于线程安全。

解码时 send_packet/receive_frame 不保证一包对应一帧，编码同理。
send 返回 EAGAIN 时应先 receive 消耗输出，再重试同一输入；
结束输入后发送空输入进入 drain，继续取输出直到 EOF。
这些流程属于 Phase 2，本阶段没有实现。
未来使用 unique_ptr + 自定义删除器管理资源，异常或提前返回也能释放。

### 解封装、解码、编码和封装

解封装从容器中分离出带 stream_index 和时间戳的 packet；
解码输出 frame；视频滤镜/音频混音处理 frame；编码重新生成 packet；
封装把 packet 和流参数写入 FLV/MP4 等容器。
Phase 1 的 Remux 跳过解码和编码，重点是流映射、封装兼容性和时间戳；
不能认为任意输入编码都能直接写进普通 RTMP/FLV。

### PTS、DTS 与 time_base

PTS 表示显示时刻，DTS 表示解码时刻。B 帧可能导致二者不同，
不能无条件令 DTS=PTS。时间戳 t 的秒数为 t × time_base.num / time_base.den。
例如输入时间基 1/90000，PTS=90000 对应 1 秒，转换为 1/1000 后是 1000。
应使用 av_rescale_q 或 av_packet_rescale_ts 做整数有理数换算，避免浮点累计误差。

输出 stream 的 time_base 可能被封装器在写头时修改，必须读取写头后的值。
AV_NOPTS_VALUE 是未知时间戳，不能直接参与普通加减运算。
音频时间基常用 1/sample_rate；帧时长按 nb_samples 推导，
视频时长按帧率或源时间戳推导，不能把毫秒常量混用进采样单位。

多源即使时间基相同，原点和设备时钟仍可能不同；需要归一化起点、
建立共同媒体时间轴并处理漂移。日志 system_clock 可跳变，适合人读的时间；
运行耗时和实时调度应使用单调时钟。当前程序不执行上述媒体换算或同步。

### C++11 日志的并发与 RAII

Logger 每条记录持有 lock_guard，锁覆盖格式化、输出和刷新。
线程异常离开作用域也会解锁；过滤阈值构造后不可变，因此并发读取无需单独加锁。
gmtime_r 使用调用者的 tm，避免共享静态时间缓冲。
转义换行防止外部输入伪造多条日志。输出流和 Logger 必须活到全部线程 join 后。
多个 Logger 即使写入同一 ostream 也不会共享锁，因此约定同一输出流共用一个实例。

同步输出没有队列增长风险，但慢终端会阻塞业务线程；
未来如引入异步日志或媒体队列，必须有容量、关闭唤醒、背压/丢弃策略，
不能用无限队列掩盖生产消费速度差。音视频数据的丢弃还要考虑关键帧依赖、
音频连续性和延迟预算；具体策略在相应阶段实测后决定。

视频合成需要统一像素格式、尺寸和调度时刻；音频混音需要统一采样率、
声道布局和对齐采样区间。RTMP 重连要重新建立输出上下文并处理关键帧及时间戳。
这些是后续阶段的关注点，不在 Phase 0 增加空壳实现。

## Phase 1：单路输入与不转码转推（2026-10-29）

本节是当前实现；上文 Phase 0 的“尚未实现”描述保留为历史记录。
当前链路：StreamInput → AVPacket → 时间戳转换 → StreamOutput。
没有调用解码器或编码器，没有 AVFrame。外部 FFmpeg 命令只生成测试素材和独立验证。

### 输入探测与流参数

avformat_open_input 打开容器/协议，avformat_find_stream_info 探测流信息，
av_read_frame 逐次返回压缩包。文件扩展名不决定真实媒体格式。
每个包的 stream_index 对应输入上下文的 streams 数组，不能假设 0 永远是视频。
本实现遍历流并验证最多一路 H.264 和一路 AAC，忽略字幕等非音视频流；
因为策略是严格拒绝多音轨而非自动选最佳流，不需要调用 av_find_best_stream。

输出 avformat_new_stream 建流后，用 avcodec_parameters_copy 复制参数，
包括 H.264 SPS/PPS 或 AAC AudioSpecificConfig 等 extradata。
codec_tag 清零，让 FLV 封装器选择适用标签。Remux 不使用
avcodec_parameters_from_context，因为不存在编码器上下文。
H.264 的 AVCC/Annex B、AAC 的带头/裸负载不是同一种表示；
当前让 FFmpeg 封装器处理支持的输入表示。本地 MP4 已验证，不能据此宣称
任意 RTSP 摄像机或任意 AAC 表示均已兼容。

### 包结构和缓冲引用是两层资源

make_packet 分配一次 AVPacket 结构，unique_ptr 自定义删除器最终调用
av_packet_free。每次 read 前 av_packet_unref 清理旧缓冲引用；
忽略流、异常退出和提前停止都不会遗留循环中的当前包。

av_interleaved_write_frame 会接管引用计数包的缓冲引用，并将调用者的包清空，
包括函数返回错误的情况。因此必须在调用前读取索引、时间戳和统计信息；
不得在写失败后原样重试这个已经被消耗的包。
结构本身仍归 unique_ptr，下一次可以复用。
如果未来跨线程排队，需要转移结构所有权或显式 ref/move_ref，
不能把同一个循环复用的 AVPacket* 分发给多个消费者。
当前没有媒体线程/队列，也没有 AVFrame 生命周期问题。

输入上下文使用 avformat_close_input；输出上下文不能拿这个函数释放，
而是先关闭输出 I/O，再 avformat_free_context。
本地自定义 AVIO 的 buffer 可能被 FFmpeg 替换，因此释放的是
context->pb->buffer，而不是保存最初传入的地址。
本实现直接检查本机 FFmpeg 6.1 头文件中的所有权说明。

### B 帧、共同原点和毫秒量化

样片视频 time_base=1/12800，音频为 1/48000；
FLV 写头后两路变成 1/1000。因此必须先 avformat_write_header，
再以当前输出 time_base 调用 av_packet_rescale_ts，
同时转换 PTS、DTS、duration。

使用第一个选中包的 DTS 转成微秒作为共同原点，换回每路输入时间基后，
同时从它的 PTS 和 DTS 中减去对应偏移。
同一路 PTS-DTS 不变，不同流之间的相对起点保持，最多引入整数舍入误差。
不能各自减去各自第一包时间戳，否则人为消除原本存在的 300ms 音频延迟。

含 B 帧的视频首 DTS 为负是正常情况；不能简单丢弃负 DTS 或令 PTS=DTS。
当前示例视频首 DTS=-0.080 秒、首 PTS=0，统一平移后 DTS=0、PTS=0.080 秒。
音频首时间戳随同一个原点移动，而不是单独从 0 开始。
后续若仍出现负时间戳，输出上下文设置 MAKE_NON_NEGATIVE 交给封装器处理。

测试逐包比较输入/输出压缩数据 SHA-256，比较每一路 DTS 单调性、
所有流的共同平移量和 PTS-DTS 差值，允许小于 2ms 的换算误差。
这比仅检查“文件存在”“播放器能打开”更能发现 Remux 中隐蔽的时间轴错误。
AAC priming/padding 的容器表达可能变化；当前没有承诺采样级首尾裁剪完全一致。

缺失 PTS/DTS、不严格递增 DTS、损坏包都明确报错。
不能通过随意加 1、覆盖 DTS 或强制生成时间戳来掩盖问题。
本阶段也没有实现设备时钟漂移、跨源时间轴对齐或时间戳回绕恢复。

### 文件的实时发送节奏

本地文件可远快于播放速度读完，直接向 RTMP 写入会造成突发流量或缓存积压。
当前以 DTS 为调度依据：
目标经过时间 = 当前 DTS（微秒）- 第一个 DTS（微秒）；
实际经过时间 = av_gettime_relative() - 启动时单调时钟。
目标在未来才等待，落后时立即继续，等待切片最大 10ms。
不按每包固定睡眠，因为音视频包交错、帧率和音频包时长不同。
也不能按 PTS 调度 B 帧编码包，否则重排序会干扰发送节奏。
3 秒样片实际发送约 3.09 秒，与最后 DTS 和启动开销相符。

单线程天然把输出速度反馈给输入，不产生自建无限队列。
这不代表端到端低延迟：协议、FFmpeg 内部交织和接收播放器都有缓冲。
max_interleave_delta 只限制交织等待的媒体时间跨度，不是字节容量上限。
后续性能阶段才研究背压、丢帧、队列容量和独立输出线程。

### I/O 超时、EOF 和停止

IoControl 在每次打开、探测、读取、写入前设置新的单调截止时间。
AVIOInterruptCB 查询截止时间和停止标志，避免永久卡在网络 I/O。
持续 EAGAIN 另有“最后成功读包时间”计时，避免反复重置超时导致无限等待。

SIGINT/SIGTERM 处理器只写 volatile sig_atomic_t；不做日志、锁或资源释放。
主循环发现停止后尽力写 trailer。写尾暂时忽略停止标志，但仍保留 I/O 超时，
避免 Ctrl+C 后完全不写尾，也避免清理阶段无限等待。
正常完成的显式 finish 检查写尾、flush、关闭错误；析构只做不抛异常的资源回收。

复查发现某些协议可能把中断表现为 EOF，因此读取结果为负时先检查
用户停止/截止时间，再解释 EOF。文件 EOF 是正常结束；网络 EOF
只说明连接结束，无法确定是主播主动停播还是断流，本实现返回失败并记录，
不冒充已实现自动重连。真实会话中途断流仍需要已有服务端测试。

回调不是强制终止系统调用的机制，DNS 或内核磁盘阻塞未必及时返回；
不能把 timeout_ms 宣称为所有操作严格的墙钟上界。
网络中断后的部分 FLV 也不能自动当作完整节目输出。

### 输出文件保护

普通 avio_open 的写模式会截断现有文件。为了保护已有工作，
本地输出用 open(O_CREAT|O_EXCL) 原子创建，再交给自定义 AVIO 回调写入。
这避免“先判断文件不存在，再打开”之间的竞争，也拒绝已有符号链接。
本地路径与输入相同、经符号链接指向输入、已经存在的输出均已验证不被修改。
失败后保留本次创建的部分文件便于排查，不自动删除或覆盖用户文件。

### 本次问题定位与测试边界

第一次集成测试在素材命令 -itsoffset .3 失败，本机 FFmpeg 要求 0.3；
已修正生成命令并重新执行完整测试，没有跳过偏移验证。
故障测试通过修改 FLV 标签注入重复 DTS，通过 RLIMIT_FSIZE 触发真实写入失败。
网络超时测试只接受 TCP 连接而不回应协议，不伪装成成功 RTSP/RTMP 服务。

Debug、Release 和 ASan/UBSan 都执行同一套 CTest，覆盖正常和失败释放路径。
短测试未报告内存问题不等于长期稳定性已证明，系统 FFmpeg 库也未用本项目
编译参数重新构建。成功 RTSP/RTMP 会话、人工视听和长期运行仍待验收。

## Phase 2：编解码与转换

解码器 send_packet 不接管调用者的 AVPacket；调用成功后可以 unref，
但 EAGAIN 时先 receive 消耗输出，再重试同一个输入。
receive_frame 的结果用 unique_ptr 持有，回调通过 move 接收唯一所有权。
B 帧意味着解码输出延迟，EOF 必须 send nullptr 并 receive 到 EOF。
编码器 send_frame/receive_packet 采用对应状态机，不能把 EAGAIN 当作结束。
本实现每次 send 后主动排空输出，flush 后仍收到 EAGAIN 则明确报错。

完整收尾顺序为：视频解码器→视频编码器；音频解码器→重采样器→FIFO 尾块→AAC 编码器；
最后写容器 trailer。53 帧含 B 帧素材、27 帧 H.265 素材均无尾帧丢失。

sws_getCachedContext 依据输入尺寸/像素格式缓存或重建转换器，输出 YUV420P；
当前固定目标尺寸会缩放画面，不提供保持宽高比的选项。
音频使用 FFmpeg 新 AVChannelLayout API，swr_alloc_set_opts2 设置
输入格式与目标 48kHz/双声道/FLTP。swr_get_out_samples 估算输出空间，
swr_convert 的实际返回值才是本次可用采样数，不能假设输入输出数量相同。
重采样产生的延迟必须用空输入继续排空。

AAC 通常一次要求 1024 个采样；AVAudioFifo 聚合重采样输出，
正常块按 frame_size 发送，末块按原生 AAC 支持的小尾帧发送。
FIFO 上限 192000 采样（4 秒），超过则报错；不是无限缓冲。
编码时间戳按实际送入采样数递增，而不是按输入包数推导。
首次采样 PTS 来自归一化后的源帧时间，保留音视频相对起点。
音频编码预卷和末端填充可造成约一帧的首尾偏移；测试允许明确的帧级容差，
这不等于采样级无缝裁剪或人工视听验证。

输入源使用容器 start_time 作统一原点（缺失时首个解码帧回退），视频 encoder
time_base=1/90000，音频=1/48000。封装前再转成实际输出流 time_base。
缺失帧 PTS、视频回退、音频参数变化和明显间断均拒绝；不提前实现漂移修复。

## Phase 3：有界队列、调度与视频滤镜

### 为什么输入解码和输出调度分线程

单线程串行读取四个网络源时，一路 read 阻塞就会拖住所有画面。
现在每路 VideoSource 在独立线程中拥有 StreamInput、MediaDecoder 和 swscale，
只有主线程拥有 VideoMixer、编码器及输出上下文。没有多个线程并发调用同一
AVCodecContext 或 AVFormatContext，也没有 detach。

工作线程遇到异常时记录日志、设置原子失败状态并关闭队列，主线程保留其他源。
退出先关闭所有队列，唤醒满队列上的生产者，再 join；否则主线程如果直接 join，
生产者可能永远等不到消费者腾出空间。独立 I/O 中断控制使用 atomic<bool>，
避免把普通 volatile 标志误当成跨线程同步。帧队列数据由 mutex 保护，
condition_variable 的等待都有状态谓词，以处理虚假唤醒。

### 帧所有权和有界内存

解码回调先将像素转换到统一尺寸，再把 unique_ptr<AVFrame> 移入 FrameQueue。
队列最多 8 帧，满时阻塞。主线程取走后成为唯一结构所有者，
下一次更新最近帧会自动释放旧 AVFrame。
真正进入滤镜时 av_frame_ref 创建缓冲引用，再交给 buffersrc；
即使最近帧被替换，滤镜的缓冲引用仍有效。

“8 帧上限”是应用队列的上限，不包含解码器内部参考帧、最近帧、编码器或滤镜缓存。
每帧尺寸也影响内存；640×360 YUV420P 原始有效像素约 345600 字节，
四路队列 4×8 帧约 10.5MiB，实际还要加对齐和其他缓存。
不得直接把这个估算当作实测进程内存。
FrameQueue 单测验证了满队列背压、按时间选择、关闭唤醒生产者和消费者。

### 15/24/25/30fps 如何统一成 20fps

每个输入把首帧 PTS 换成微秒并作为自己的零点。主线程输出 tick=k，
目标媒体时间 t=k/20 秒。每路取 PTS≤t 的最新帧：
高帧率源的中间帧被替换，低帧率源在没有新帧时重复最近帧。
未来帧留在队列中，不能为了追求“最新”提前播放尚未到时间的画面。

实时模式按单调时钟输出，不在每帧等待慢源；离线模式有限等待未来帧或 EOF，
避免 CPU 调度差异让本可获取的本地帧被误判为缺失。
最近帧超过 stale_ms 后使用黑帧，所有源仍在同一个输出 tick 上向滤镜供帧。
否则 xstack/overlay 的多源同步可能等不到某路输入，卡住整个输出。
首帧归零只代表软件假定各源同时开始，不提供 NTP、设备时钟或采集时刻对齐。

单测之外，集成测试用起点为 5 秒、1 秒时从红色变白色的 15fps 视频，
验证归零后输出的 20fps 画面在正确时段变化，避免只测静态色块遗漏调度错误。

### libavfilter 图和布局切换

各路 buffer 描述固定尺寸、YUV420P、time_base=1/fps；
split 使用 scale+hstack，grid 使用 scale+xstack，pip 使用 scale+overlay。
输出通过 buffersink 取帧，逐帧检查 sink PTS 与调度 tick 一致，
再转成 H.264 编码器的 1/90000 时间基。

所有布局都同步供入相同 tick 的帧，每轮输出一帧，没有依赖未来帧的 fps 滤镜。
所以布局切换时可以释放旧图、建立新图而不丢失待输出帧；
编码器保持原样，切换后 PTS 沿原时间轴继续。
切换时间不是任意毫秒的精确显示时刻，而是该时刻之后第一个输出帧边界。

滤镜输入端点列表由 parse_ptr 修改，正常和异常路径都释放当前列表头；
滤镜图最终通过 avfilter_graph_free 释放。
测试通过读取四宫格、双画面和画中画指定区域的实际 RGB 像素，
确认输入不是串位或只覆盖了一路。编码压缩误差用明确的像素容差处理。

### 当前局限与实测结论

Phase 3 输出仅视频；混入虚构静音轨或随意选择一路音频都不能代替 Phase 4 混音。
四路不同分辨率和帧率输入的 2 秒片段输出 40 帧/20fps，
布局切换保持连续 PTS。短源 EOF 后超期变黑，另一源持续正常输出。
四路满队列时 SIGINT 能退出，Release 和 ASan/UBSan 均通过六项测试。

CPU 调度落后、日志阻塞和输出网络阻塞仍会影响实际延迟，
不能根据有界队列或 x264 zerolatency 参数声称端到端超低延迟。
还未验证多路 1080p、24 小时稳定性、成功 RTMP 播放或多设备时钟同步。

## Phase 4：PCM 混音、采样主时钟与漂移补偿

### 音频为什么不能按视频取“最新一帧”

视频重复/跳过一帧通常表现为停顿或运动不连续；音频丢一块 PCM 会产生时间缺口，
可能听到爆音。FrameQueue 的“最新帧”规则不适用于音频。
AudioQueue 中的 pts 单位是 1/48000 秒，每块覆盖 [pts, pts+nb_samples)。
主线程请求明确采样区间，只复制交集；缺口补零，未来块保留，过期块丢弃并计数。
一个块可以跨多次读取，不能在第一次读取后把尚未消费的尾部丢掉。

队列最多 32 块、每块最多 8192 采样。双声道 float 数据上限约
32×8192×2×4=2MiB/路（不含解码器、重采样器和分配开销）。
这是明确的块容量上限，不能根据常见 AAC 1024 采样假定所有输入都是同一时长。
满队列反压工作线程；关闭后唤醒阻塞 push，停止所有源后再 join。

### AAC / Opus 和所有权

现有 MediaDecoder 新增 Opus codec_id，仍使用 send_packet/receive_frame，
解码出的 AVFrame 由回调接收唯一所有权，转换后的新帧移动进音频队列。
AAC 可能来自 MP4，Opus 常见于 Ogg；容器、压缩算法和解码后的 PCM 布局是三层概念。
统一使用 FFmpeg 6.1 的 AVChannelLayout，将各种采样率/声道布局转换成
48kHz、双声道、FLTP。FLTP 每个声道各一块 float 数组，不能当成交错 LRLR 数据。
主线程混音前创建独立的目标区间 PCM 帧，拥有缓冲；不会修改工作线程共享的源帧。

### 音量、静音和峰值保护

每个采样先计算 y[c,n]=Σ gain[i,n]×x[i,c,n]，不自动除以源数量。
因此静音某一路不会改变其他路的响度。静音仍消费音频队列，避免恢复时播放旧声音。
增益在 240 采样（5ms）内从当前值过渡到目标值，避免瞬间跳变带来的阶跃。
动态控制在音频块边界生效，不能声称精确到任意毫秒。

相加后用双声道共同峰值计算限制增益，编码前绝对峰值目标 0.95；
需要衰减时快速降低增益，恢复时约 100ms 回升，避免反复硬截断。
这会改变过载内容的动态范围，不是“完全无失真”的保证。
正常电平测试检查两路频率幅度、增益比例及额外谐波；过载单测检查 PCM 峰值。
AAC 是有损编码，解码后的重建峰值不能保证与编码前 PCM 完全一致。
异常输入切换点还没有交叉淡化，仍需人工听感验收。

### 统一原点与真实设备的边界

Phase 3 各视频首帧归零；Phase 4 优先使用容器 start_time（或流 start_time 最小值）
作为同一文件音视频共同原点。这保留“音频本来晚 250ms”的关系。
缺少这些信息时音频回退到首帧并记录警告，不能恢复本来未知的跨轨关系。
不同文件默认视为共同开始，用户可用 audio-offset-ms/video-offset-ms 配置设备偏移。
提前到负时间的采样会被裁掉，延迟前的区间补静音/黑帧。

当前音频和视频用独立解复用连接，避免一个音轨满队列阻塞同一解复用线程、
再让视频消费者等待而形成循环等待。代价是同一 URL 打开两次；
文件时间戳可复现，网络连接可能观察到不同起点，不能据此宣称完成真实设备同步。
后续若整合为单次解复用，应设计不会因任一路满队列而死锁的联合背压策略。

### 重采样的相位误差与补偿

输出的采样位置 next 只包含已经从 swr 取出的采样；swr 内部还有滤波延迟。
当前输入帧应该对应的位置预测为：

predicted = next + swr_get_delay(context, 48000)
error = mapped_input_pts - predicted

忽略延迟会把滤波器正常缓存误判为设备漂移，造成不必要的拉伸。
误差超过 24 采样（0.5ms）时，用 swr_set_compensation 设置未来 48000 采样中的
增减量，单次幅度限制 ±240（约 ±5000ppm）。输入时钟较快、正误差增大时，
需要逐渐多输出采样，覆盖更长的目标媒体时间，而不是简单覆盖帧 PTS。
每帧重新计算反馈误差，避免凭浮点时间逐帧累计。

600 秒加速模拟中，输入 PTS 按 ±1000ppm 变化，最终误差为 48/46 采样，
峰值为 49/48 采样。约 1ms 的有界残余来自反馈补偿，不能写成“零误差”。
这是输入 PTS 模拟，不是从真实声卡采集运行 10 分钟。

超过 100ms 的相位差按间断处理，清理旧重采样缓存并重新定位，队列缺口补静音。
缺失时间戳按上一帧末端重建；重复/回退或大于 2 秒的异常跳变重新建立 epoch，
后续继续沿连续输出时间轴走。错误计数和峰值误差可从源日志观察。
合法但超过 2 秒的源停顿也会被这项策略视为跳变，这是明确的第一版策略边界。
音频格式中途变化目前将该源降级静音，不假装已经完成动态重配置。

### 采样主时钟和三个不同的“误差”

输出视频 tick/fps 与音频 cursor/48000 通过 av_compare_ts 比较，
优先生成较早的媒体事件。视频转换到编码器 1/90000 时间基，音频保持 1/48000，
最后通过 StreamOutput 转成容器实际时间基。源视频的慢/快漂移通过选帧、重复或跳帧处理，
不修改输出节奏；源音频则通过重采样补偿保持采样连续。

必须区分：

- 源相位误差：输入 PTS 与已经生成/缓冲的音频采样位置之差，单位采样。
- 输出调度差：已送编码的视频末端减音频末端，单位微秒；有一帧或一块的粒度。
- 内容音画差：画面事件与声音事件在输出中的真实时间差，需要测内容。

25fps 下调度差出现 40ms 不意味着内容晚了 40ms。
CSV 每约 1 秒和结束时记录调度位置，wall_lag_us 则反映单调时钟与媒体进度，
离线快速编码时该值为负，不是播放时钟出错。
30 秒输出记录 31 个采样点、调度差不累积；实际设备长期漂移仍需另外验收。

### 测量错误的定位

第一次内容校验允许一帧误差，观察到约 -41ms，进一步复核发现：
FFmpeg 导出原始视频的默认帧率同步会补帧，数组下标不能直接当原视频时间戳。
改为 -fps_mode passthrough，并把逐帧数据与实际视频包 PTS 对应，
同时检查导出帧数没有变化，避免测量工具改变被测对象。
修正后，原有 250ms 偏移测为 249ms；提前 250ms 后内容差为 -1ms。
音频事件以 10ms RMS 窗口检测，不能把 -1ms 当作测量精度达到 1ms 的证明。
测试容差从 50ms 收紧到 20ms，Debug/Release/ASan 均通过。

Phase 4 结束时尚未部署 RTMP 服务端，也未实现 Phase 5；后续实现见下方 Phase 5 记录。


## Phase 5：输出阻塞、所有权与关键帧恢复

### 为什么使用独立输出线程

av_interleaved_write_frame 不只是复制内存，它可能触发协议发送并等待网络。
把它放在合成线程中会冻结媒体时钟，使输入背压和输出积压相互传递。
本阶段将封装器、AVIO 和 I/O 超时控制全部交给 AsyncOutput 工作线程；
主线程仍独占两个编码器，输出线程仅使用复制的 AVCodecParameters 和时间基。
没有跨线程并发调用同一个 AVCodecContext 或 AVFormatContext。

AVPacket 的 unique_ptr 通过 std::move 从编码回调交给队列，再交给输出线程。
队列关闭、丢弃或异常退出时由 RAII 释放。av_interleaved_write_frame 会接管引用，
写失败也不能假定原始包仍完整。因此错误恢复不重试该对象，重新等后续关键帧。
统计所需的包类型、大小和原 DTS 必须在写入前保存；写入后 packet 可能已经被清空。
AVFrame 的所有权仍沿用 Phase 4：输入线程拥有解码帧，队列移动所有权，滤镜持有自身引用；
编码回调同步完成送帧，输出线程从不访问这些帧。

### 三种容量和两种输出策略

仅限制包数不够：一个 IDR 可能比许多音频包更大；仅限制字节也不够：
静态画面码率很低，却可以缓存很长媒体时间。本阶段同时限制包数、字节和 DTS 时间跨度。
取出时另检查 av_gettime_relative() - queued_us，发现墙钟上的陈旧数据。
本地文件允许生产者阻塞，保持完整节目；实时 RTMP 过载则清空旧窗口，并请求新 IDR。
这里丢弃的是一个不能再满足延迟要求的节目区间，音频也跟随丢弃，避免各自独立追赶。

队列每次清空递增 epoch。已经出队的包若属于旧 epoch，写入前再次检查并丢弃。
检查和实际网络写入之间仍可能发生并发清空，已经进入 I/O 的数据不能撤回；
后续发现 epoch 改变时关闭旧连接，从新会话恢复，避免把旧内核缓冲继续当作实时数据。
积压触发的重连也消耗总恢复预算，避免网络持续过慢时无限重建连接。

### IDR、媒体头与共同时间原点

P 帧依赖前面的参考图像，随意丢一个压缩包后接着发送后续 P 帧可能花屏。
编码器启用 forced-idr，主线程看到恢复请求就把下一帧 pict_type 设为 I，
让 libx264 输出真正的 IDR；输出端必须等待带 KEY 标志的视频包。
每次新会话创建新的封装上下文、复制 H.264/AAC 参数，重新写 FLV 媒体头和序列信息。
这使接收端可以重新得到 SPS/PPS 和 AAC AudioSpecificConfig。

设新会话首个 IDR 的 DTS 转为微秒后是 origin_us，则每路输出时间戳都减去同一原点：
PTS_out = rescale(PTS_in, encoder_tb, mux_tb) - rescale(origin_us, 1/1000000, mux_tb)。
DTS 同理。实际实现通过公共 StreamOutput 完成整数重标定，并以写头后的时间基为准。
不能分别把音视频首包都归零，否则会抹去原本的相对偏移。
早于视频原点的 AAC 包丢弃，其余保持相对时间；AAC 编码延迟不应靠随意改时间戳掩盖。
恢复期间节目内容会有缺口，这不等于无缝恢复。

### 超时、退避和退出

每次打开/写入前为 AVIOInterruptCB 设置单次期限。失败后销毁旧输出上下文，
等待 min(4000ms, backoff × 2^n)，退避可被 condition_variable 唤醒取消。
默认整次运行最多5次自动恢复，成功连接不重置预算；0 禁止自动恢复。
握手比队列预算更慢时，已建立但尚未发送媒体的新连接保留，等待更新的 IDR，
避免因握手本身较慢而反复重连。输入结束仍未恢复必须报错，不能以退出0伪报成功。
信号由主线程接收，原子取消标志由工作线程读取；收尾等待期间仍检查信号，最终 join。
FFmpeg 中断依赖底层调用检查回调，不能承诺任意 DNS/文件系统内核阻塞均严格限时。

### 低延迟参数和测量边界

H.264 使用 zerolatency、无 B 帧、无前瞻、可配置 GOP/VBV；降低缓冲会影响码率稳定性和画质。
VBV 字节缓冲由码率×时长换算，不能把 VBV 时长当作实际延迟。
封装降低 max_interleave_delta，并主动 avio_flush；这不代表 TCP 对端已收到或播放器已显示。
输入默认队列减为4视频帧、16音频块，仍可配置；旧程序保留原默认容量。

平均 fps = 成功交给封装器的视频包数 / 墙钟秒数；编码数据 kbps = 字节数×8/秒/1000。
丢包率 = 丢包数/(成功包数+丢包数)，调度阶段跳过的未编码帧/采样另外计数。
排队峰值和写入峰值用于定位应用内部瓶颈，不包括播放器缓冲，也不是端到端延迟。
要测真实直播延迟，应在采集画面叠加可比较的时钟/事件，再在播放器观察同一事件；
同时记录网络、接收端、播放器缓存及音视频内容偏差，不能只看本程序的 CSV。

本阶段用真实编码器和 FLV 封装器验证注入断流、慢写入、重新写头、IDR 起点和独立解码；
同时测试 FFmpeg RTMP 的连接拒绝和握手超时。未提供真实接收端，成功 RTMP 恢复和延迟仍待测。


## Phase 6：独立录制、容器收尾与关键帧回放

### 一次编码，多路封装，所有权如何分离

本阶段的数据流为合成/混音 → H.264/AAC编码 → 两个输出分支。
直播沿用AsyncOutput，录制新增Recorder工作线程，不增加一套解码/编码器。
编码回调先用av_packet_clone创建录制分支的AVPacket，再把原包move到直播队列。
clone复制包头并增加底层数据缓冲引用计数：PTS/DTS/stream_index可以分别修改，
压缩数据共享且不修改。不能把同一个AVPacket*同时交给两个封装器，
因为av_interleaved_write_frame会消费引用并重写包状态。
每条支路的unique_ptr独立释放其AVPacket，最后一份引用释放时数据缓冲才回收。
AVFrame仍只在输入/处理/编码链路中流转；录制不持有解码帧。

Recorder启动前用avcodec_parameters_from_context复制编码参数，工作线程独占
StreamOutput、AVFormatContext、AVIO和索引FILE。主线程不会调用录制封装器。
队列用mutex与condition_variable保护，最多1024包且默认16MiB，包含side_data字节。
submit不等待磁盘：达到容量就停止录制、释放排队包、记录ERROR，让直播继续。
它不会随意丢P帧后继续伪造完整录像。成功写出的有效部分可以正常收尾，
但异常录制日志仍保留；整体进程退出0仅表明直播主链路正常。

### MP4与Matroska为什么必须正确写尾

复用StreamOutput的avformat_alloc_output_context2/avformat_new_stream/
avformat_write_header/av_interleaved_write_frame/av_write_trailer。
新增加mp4和matroska格式选项，既有FLV调用仍使用原默认格式。
本地自定义AVIO同时实现write和seek，便于MP4回写容器元数据，且使用O_EXCL防止覆盖。
每个容器写头后重新读取stream time_base，不能假定MP4和MKV都使用FLV的1/1000。

普通MP4通常在写尾时生成关键的moov索引；没有正常收尾的当前段可能不可播放。
因此本阶段在finish成功之后才写TSV索引行，避免把失败段登记成已完成录像。
旧段成功写尾后才开下一段，已完成段与后续失败隔离。SIGINT会关闭生产端、
排空已有录制包并写尾，然后join；SIGKILL或断电不执行RAII，不能保证当前MP4有效。
fflush不是fsync，当前方案不宣称断电持久化。MKV也不等于任意损坏都可恢复。

### IDR切段和音视频时间基

每当视频关键帧DTS达到本段起点+segment_ms，就在写入该IDR前结束旧段。
新的文件从该IDR开始，参数来自同一编码器快照，可独立解码。
如果GOP为1秒、目标分段1.4秒，实际通常在2秒的IDR处切段；不强行把P帧当段头。
索引记录节目时间，分段文件内则减去新段首IDR的共同微秒原点。
例如节目视频DTS=90000、time_base=1/90000，音频DTS=49152、time_base=1/48000：
共同减去1秒后，视频为0，音频仍保留24ms相对偏移，不各自独立归零。
相邻索引使用半开区间[start_us,end_us)，已切段的旧段end等于下一段start，避免索引重叠。

AAC有编码延迟。收到新IDR之后，还可能收到DTS早于新段原点的AAC包。
当前基础实现丢弃这部分旧音频预卷，不写负时间戳；这可能在段边界留下音频缺口。
没有声称采样级无缝拼接。要做到无缝，需要对编码器延迟、包跨界和容器trim信息
作更完整处理，通常还需要带前瞻的音视频包排序/边界缓存或精确解码重编码。

### 索引、定位和片段提取的精度

Recorder的TSV索引映射节目时间到已完成文件，文件内关键帧位置由FFmpeg容器索引负责。
esports_replay --list-keyframes实际扫描AVPacket的KEY标志，报告时间和pos；
pos在部分输入上为−1，不能把字节位置当作普适的直接解码入口。
--index首先定位目标分段，把节目时间换成该段局部时间，再调用av_seek_frame。
AVSEEK_FLAG_BACKWARD向前定位关键帧，avformat_flush清理解复用状态，然后读取到首个KEY视频包。
输出新容器前重新写头，音视频都减去同一实际起点。

请求[1.4s,2.1s)而前一个IDR位于1.0s时，输出从1.0s开始，包含28个25fps视频帧。
终点仍是请求起点+时长，不改成实际关键帧起点+时长。压缩包本身不能切一半，
尾部AAC块或视频帧的持续时间可稍微超过请求终点。
第一版针对项目自身无B帧H.264/AAC录像，明确拒绝B帧输入，避免忽略参考帧重排问题。
跨分段自动拼接尚未实现，正时长跨界请求明确拒绝，0时长只到选中段EOF。
索引路径为绝对路径，移动文件后必须更新索引；损坏索引/越界时间/缺失录像都报错。

### 回放是带节奏的重新封装

extract模式尽快读写，适合生成精彩片段；replay模式则按DTS控制发送时刻：
目标墙钟 = 启动单调时钟 + 当前DTS微秒 - 实际起点微秒。
必须使用DTS而不是简单每包sleep固定间隔，因为音频和视频包的间隔不同。
循环检查SIGINT/SIGTERM，每次短等2ms；写出由FFmpeg C API完成。
输出可选MP4/MKV/FLV，RTMP只允许replay实时模式。
这是独立回放输出，不是将回放画面动态切入正在运行的节目，也没有新增回放自动重连。

### 本阶段定位的测试错误

第一次测试把普通直播FLV与独立录制分段都要求首视频DTS=0，导致异常隔离测试失败。
实际原因是直播FLV保留负DTS的AAC预卷，容器统一平移后首视频约为21ms；
录制则丢弃新IDR以前的AAC，因此分段首视频为0。
修正测试为分别检查直播约21ms和录制0ms，并继续严格验证DTS递增、包哈希和完整解码。
这没有通过改写被测媒体或泛化容差掩盖时间戳问题。

Debug/Release/ASan+UBSan各11/11通过，具体数据见测试报告。
实际RTMP边播边录、人工视听、磁盘写满/断电、慢盘长期背压未实测。
输出线程隔离的是正常运行时的磁盘等待，最终join仍可能等待内核阻塞的文件写入。


## Phase 7：指标口径、性能采样和引用计数优化

### 先区分不同的时间

媒体时间来自PTS/DTS和time_base；性能计时使用av_gettime_relative单调微秒时钟；
CPU时间来自getrusage的用户态+内核态累计值。这三者不能混用。
CPU窗口百分比 = ΔCPU微秒/Δ墙钟微秒×100，多线程进程可超过100%，
不能直接拿100%作为整台24逻辑核机器的上限。
输出FPS由相邻采样窗口成功写出的视频包计数求差，输入FPS来自解码帧计数。
文件输入预读会使启动FPS暂时很高；输入阻塞和有界队列背压会降低解码速率。
逐源v0_frames等保留原始计数，避免只看总数而遗漏一路提前结束。

### 如何不把背压错算成编解码性能

MediaDecoder/MediaEncoder为每次avcodec_send_packet/send_frame/receive_frame/receive_packet
单独计时；consumer回调在计时外执行。否则回调里满队列等待或磁盘/网络背压
会被统计为“编码器很慢”，导致错误优化方向。
统计累加在原子计数器中，解码器由输入线程独占，主线程只读取计数。
单个字段读取安全，但整个进程所有字段不是严格同一瞬间的事务快照。

FFmpeg内部使用帧/切片线程时，send/receive调用的墙钟耗时不能完整代表后台线程CPU耗时。
本阶段单独统计合成/混音调用，不把输入swscale和重采样混入该指标。
因此decode_us+encode_us+processing_us不是进程CPU总量，也不能相加作为端到端延迟。
RSS来自/proc/self/status，峰值RSS来自getrusage；Linux不同来源的更新口径有差别，
采样时RSS也会漏掉两次采样之间的峰值。长期泄漏需观察充分预热后的趋势，
不能仅凭结束RSS低于启动RSS或短期ASan通过就作出结论。

### perf证据与局限

本WSL环境能运行perf软件事件cpu-clock，cycles/instructions探测返回not supported。
使用99Hz软件采样，对四路1080p输入合成1080p/30fps同时录制运行10秒。
初次采样712个样本，丢失0；按动态库归属约38.34%在libavcodec、29.92%在libx264、
17.42%在libswscale、12.22%在libc。这是样本占比，不是函数调用次数。
perf缺少libunwind/libdw支持，部分系统库符号也不可见，只能可靠做到库级归属，
不能把libc地址武断认定为某个具体memcpy调用或声称有完整调用链。

采样结合代码检查发现，VideoConverter原先即便收到同尺寸YUV420P，也执行
av_frame_get_buffer和sws_scale，导致不必要的完整图像分配及复制。
优化后，只有尺寸与像素格式完全匹配时使用av_frame_ref共享像素；其余路径继续swscale。
不是把AVFrame*跨线程随意共享：每个消费者仍有独立的AVFrame头，
底层AVBuffer通过引用计数延长寿命。修改PTS和pict_type不影响源帧头；
输出清除输入pict_type，避免把原输入的I/P/B类型当成新编码决策。
修改共享像素必须先av_frame_make_writable触发写时复制。
新增测试实际释放源帧后读取输出，并修改可写输出检查原像素没有被污染。

### 测试必须让媒体源真正工作

run-stability.py生成比测试时长多1秒的testsrc2动态视频和正弦音频，
建立4个独立文件解复用/解码会话，按实时节奏合成与录制。
测试结束检查每路累计输入帧数，不能只看输出文件时长；否则输入早已结束后
长时间黑帧/静音会给出虚假的低CPU和低内存“稳定性”。
脚本还检查输出完整帧数、每段解码、录制成功、队列界限、进程退出及最终输出队列排空。
素材生成和解码检查属于测试辅助，核心处理仍由C++ FFmpeg API完成。

短时压力采用相同输入样片的4个独立会话，不代表4个真实网络设备。
perf会引入采样开销，重复短跑存在调度波动；单次前后对比只记录观察值，不宣称普适提升百分比。
120秒墙钟也不是24小时稳定性。真实RTMP接收播放、断网恢复、磁盘故障和硬件时钟
仍需独立验收，代码阶段实现完成不等于这些目标全部达成。


## 2026-10-30：测试工具也必须正确管理进程生命周期

使用perf record包装媒体程序时，测试工具的直接子进程是perf，而不是esports_live。
subprocess.run超时终止直接子进程，并不能证明孙进程也已停止。
因此使用start_new_session创建独立会话/进程组；超时与Ctrl+C向该组发送SIGINT，
让C++信号处理器设置停止标志、关闭队列、join并写尾；宽限后再SIGKILL。
只操作自己创建的进程组，不按程序名全局杀进程。

初次新增回归暴露了另一竞态：包装器已经退出时，wait只回收包装器；
killpg(SIGKILL)只是投递信号，后代进程可能还未被调度处理退出。
改为在有界时间内读取/proc的进程组与状态，确认该组没有仍在执行的进程。
Z/X状态已停止执行，孤儿僵尸的最终reap由系统父进程负责，不能把它说成仍在处理媒体。
若进程陷入不可中断内核I/O，SIGKILL也不能承诺立即奏效；工具明确报错，不无限等待。

温和退出不等于测试成功：即使媒体程序收到SIGINT后正常收尾，原来的超时仍需抛出，
否则长跑提前结束也会误记通过。测试分别检查假包装器/后代生命周期，以及实际媒体
超时后的FLV和MP4解码，从进程层和封装层验证退出行为。

同时修正稳定性脚本对音频的弱检查：大于0帧只能说明曾有音频，不能证明一直有音频。
对本脚本明确生成的48kHz/AAC素材，要求每路解码块数至少为floor(seconds×48000/1024)。
这一门槛不能直接推广到Opus、可变帧长或其他采样率，需要按实际样本数和时间戳另行设计。


### 录制错误不能只测试“文件打不开”

已有目录/文件冲突测试发生在打开阶段，不能证明开始写入后的错误也被正确隔离。
本次在独立测试进程设置RLIMIT_FSIZE=4096，对真实H.264/AAC编码和MP4封装施加文件上限。
Linux对普通文件写入返回EFBIG，并可能同时发送SIGXFSZ；管道写入不受该文件长度限制。
因此测试的另一支路使用真正的FLV封装，通过stdout管道传给父进程，再保存并解码，
既能制造录制故障，又不让主支路同时受到文件上限影响。没有写伪媒体或假成功返回值。

首先证明：录制写失败，Recorder记录错误、关闭支路，失败段没有进入TSV，
另一FLV支路100帧与对照组压缩包哈希一致。再检查实际esports_live，发现默认SIGXFSZ
直接杀进程（退出码−25），异常处理根本没有执行。为esports_live设置SIG_IGN后，
写调用返回EFBIG，FFmpeg经自定义AVIO将错误传播到现有收尾逻辑；主输出失败退出1。
忽略的是终止信号，不是忽略错误：错误仍明确记录，不能吞掉写失败并宣称输出成功。

av_interleaved_write_frame可能只把数据交给AVIO缓冲，错误也可能到flush或trailer才暴露。
现有StreamOutput在写入、刷新、写尾时检查错误；Recorder只有finish成功才登记索引。
因此本次特别检查失败段不登记，不能仅凭文件路径存在就宣称录制成功。
EFBIG不等于ENOSPC，也不能模拟所有断电/磁盘故障情形；这些实际验收仍未完成。

### 修正旧用例的跨运行哈希假设

本轮Release全测曾在旧recording_write_failure用例失败：它比较两次独立编码的压缩包。
随后32次并发、全部无写入故障的对照也出现多次包哈希不同，证明跨运行字节一致不能作为
该测试的可靠前提。没有因此跳过数据完整性检查，而是改为每次运行先在分流前计算SHA-256，
再与该次FLV解复用出的包逐一比较。这检验同一份编码数据经过录制分流后的完整性，
不依赖独立编码运行的确定性；依旧检查100帧、完整解码、EFBIG和失败索引。


同次摘要比较还必须考虑合法封装转换：libx264输出Annex B起始码，而FLV使用4字节NAL长度。
直接对原AVPacket与FLV包求SHA-256会把合法格式变化误判为内容损坏。
测试先把分流前的Annex B规范成AVCC表示再求摘要，然后逐包对比FLV实际数据；
没有忽略NAL内容或放宽为只比较包数。该规范化仅用于测试，不改生产封装路径。

## 2026-10-31：源码中文注释与阅读路线

本次按实际数据流补充注释：源码和头文件标明模块职责，主直播循环分为建源、建输出、
分流回调、调度、视频、音频、退出七部分。测试/脚本说明验证目的，CMake说明依赖与标准约束。
完整阅读顺序和时间单位对照见[代码阅读路线](code-reading-guide.md)。

关键阅读约定：Frame/Packet的unique_ptr负责外壳，底层媒体缓冲可共享；get只借用，move转交所有权。
录制克隆包外壳后再让推流接管原包，因为两路封装都会改时间戳。
AVFrame引用直通后，改PTS不影响别人的外壳，改像素则需要make_writable。
回调不等于线程：编解码send/receive调用回调时仍处于当前调用线程。

时间戳注释明确微秒、帧序号、采样数和编码器time_base，避免看到int64_t就直接比较。
调度音画差不是内容同步误差，输出队列延迟也不是播放器端到端延迟。
异常路径区分正常EOF排空、用户取消、输入降级、输出有限恢复、录制失败隔离。

本次代码/构建文件只新增注释，原有语句逐行保留；第三方库保持原样。

## 2026-11-09：面向初学者的源码注释

本轮对20个自有头文件、18个实现文件和7个C++测试/夹具增加中文导读与局部说明，保留全部原有代码行。
阅读每个函数时先确认三个问题：输入的单位是什么、传入指针由谁持有、当前在哪个线程。

- `Frame`/`Packet`的`get()`只借用，`std::move`转移唯一外壳所有权；`av_frame_ref`/`av_packet_clone`建立独立外壳并共享底层缓冲。修改共享像素前要`av_frame_make_writable`。
- `make_frame`只分配外壳；自行生成黑帧或PCM还需分配缓冲。解码接收函数则负责把实际帧引用放入外壳。
- 同一个40ms时刻，在25fps滤镜中是tick=1，在视频编码器中是PTS=3600（1/90000），在音频中是1920（1/48000）。裸整数大小不能直接比较先后。
- 队列返回true的语义因接口而异：视频advance表示边界已确定，不保证画面非空；音频read_window可以返回包含静音的窗口；网络PacketQueue.push成功返回也可能按策略丢包。
- 条件变量等待释放互斥锁；退出时既要停止I/O，也要关闭队列唤醒等待者，再join。只设置停止位不能解除满队列等待。
- 输出恢复必须等待新关键帧，并在握手后复查包年龄和epoch；录制失败则关闭独立支路，两种失败处理不要混为一谈。
- 测试中的模拟包只适用于队列协议验证；恢复夹具虽然使用真实编码和FLV封装，仍不能代替真实RTMP成功会话验收。

建议从`video_reference_test.cpp`理解缓冲所有权，再读`frame_queue_test.cpp`理解线程交接，最后沿`run_live`追踪完整媒体链路。
验证命令与结果见`beginner-comments-report.md`。
