## 一、项目背景与目标

### 1.1 项目背景

电竞赛事直播系统通常需要处理多个不同来源的音视频信号，包括：

- 游戏画面
- 选手摄像头
- 赛事现场摄像机
- 游戏音频
- 解说音频
- 其他远程音视频信号

这些媒体流可能采用不同的协议、分辨率、帧率、编码格式和时间基。

直播服务器需要将这些信号统一处理，实现实时解码、画面合成、音频混音、音画同步、重新编码以及直播分发。

本项目以电竞赛事为场景，使用 Linux/C++11 和 FFmpeg 自主实现音视频核心处理模块。

### 1.2 项目总体目标

开发一套可运行、可调试、可测试、可扩展的 C++ 音视频直播服务器，具备以下能力：

1. 支持 RTMP、RTSP 和本地媒体文件输入。
2. 支持多路媒体流同时接入。
3. 支持 H.264/H.265 视频解码。
4. 支持 AAC/Opus 音频解码。
5. 支持 H.264 视频编码和 AAC 音频编码。
6. 支持多路视频实时合成。
7. 支持多路音频混音。
8. 支持音画同步及多源时间轴对齐。
9. 支持将处理后的音视频推送到 RTMP 服务端。
10. 支持 MP4/MKV 录制。
11. 支持基础赛事录像回放。
12. 支持断流重连、异常处理、日志和性能监控。
13. 提供完整的测试程序、开发文档和性能测试报告。

### 1.3 当前不实现的功能

以下技术暂时不纳入必须完成的开发范围：

- WebRTC 推流和播放
- SRS 部署和集成
- 自研 RTMP 协议服务器
- NDI 接入
- Dante 音频协议
- GStreamer 集成
- WebRTC AEC/NS/AGC 音频处理
- GPU 硬件编解码
- 分布式集群和 Kubernetes

后续可以根据项目发展逐步扩展。

### 1.4 项目开发原则

**核心音视频功能必须通过 C++11 和 FFmpeg C API 实现。**

不允许通过简单执行 FFmpeg 命令行完成全部音视频处理，以此冒充自主研发。

项目必须具备真实的媒体处理链路，而不是只有接口定义或模拟数据。

每一个阶段都要能够独立编译、运行、测试和验收。

## 三、系统整体架构

### 3.1 总体处理链路

```text
              电竞赛事音视频输入
                       |
        +--------------+--------------+
        |              |              |
     RTMP输入       RTSP输入       本地媒体文件
        |              |              |
        +--------------+--------------+
                       |
                 StreamInput
                       |
                    Demuxer
                       |
                   AVPacket
                       |
                    Decoder
                       |
                    AVFrame
                       |
            +----------+----------+
            |                     |
       VideoMixer             AudioMixer
            |                     |
       视频合成                音频混音
            |                     |
            +----------+----------+
                       |
                AVSynchronizer
                       |
                    Encoder
                       |
                 H.264 + AAC
                       |
                 OutputMuxer
                       |
             +---------+---------+
             |                   |
          RTMP推流           MP4/MKV录制
             |
         RTMP服务端
             |
           播放器
```

实际实现时，音视频同步不是简单地放在混音之后执行，而是贯穿输入时间戳归一化、帧调度、合成、混音和编码输出的全过程。

系统应建立统一的媒体时间轴。

### 3.2 线程模型

推荐采用独立输入线程、处理线程和输出线程。

```text
InputThread-1 ── PacketQueue ── Decoder ── FrameQueue ──┐
                                                        │
InputThread-2 ── PacketQueue ── Decoder ── FrameQueue ──┤
                                                        │
InputThread-3 ── PacketQueue ── Decoder ── FrameQueue ──┤
                                                        │
                                                 Media Processing
                                                        │
                                              Video / Audio Mixer
                                                        │
                                                    Encoder
                                                        │
                                                  PacketQueue
                                                        │
                                                  OutputThread
                                                        │
                                                    RTMP输出
```

具体线程数量根据性能测试优化，不要求每个模块都拥有独立线程。

所有队列必须有最大容量限制。

必须处理：

- 生产者与消费者速度不匹配
- 队列积压
- 丢帧
- 输入流中断
- 线程退出
- 资源回收
- 输出速度低于编码速度
- 线程间异常传播

禁止使用无限增长的媒体队列。

## 四、核心模块设计

### 4.1 StreamInput

职责：

- 打开 RTMP/RTSP/本地媒体输入。
- 识别音频和视频流。
- 读取 AVPacket。
- 获取 stream time_base。
- 处理输入超时。
- 检测 EOF。
- 处理异常断流。
- 支持重连。
- 维护输入连接状态。

主要 FFmpeg API：

- `avformat_open_input`
- `avformat_find_stream_info`
- `av_find_best_stream`
- `av_read_frame`
- `avformat_close_input`

### 4.2 MediaDecoder

职责：

- 创建解码器。
- 读取音视频编码参数。
- 解码 AVPacket。
- 输出 AVFrame。
- 处理 EAGAIN。
- 处理 EOF 和 flush。
- 正确释放解码资源。

主要 API：

- `avcodec_find_decoder`
- `avcodec_alloc_context3`
- `avcodec_parameters_to_context`
- `avcodec_open2`
- `avcodec_send_packet`
- `avcodec_receive_frame`
- `avcodec_free_context`

### 4.3 PacketQueue / FrameQueue

职责：

- 跨线程传递媒体数据。
- 实现有界队列。
- 支持阻塞等待。
- 支持超时。
- 支持关闭队列。
- 支持唤醒等待线程。
- 统计队列长度。
- 实现必要的丢帧或背压策略。

使用：

- `std::mutex`
- `std::condition_variable`
- `std::deque`
- `std::unique_ptr`

所有权必须明确。

AVPacket/AVFrame 的传递需要正确使用引用计数、移动语义或明确的资源所有权封装。

### 4.4 VideoMixer

职责：

- 多路视频帧输入。
- 不同分辨率视频缩放。
- 统一像素格式。
- 统一输出帧率。
- 双画面合成。
- 画中画。
- 2×2 四宫格。
- 视频布局切换。
- 处理输入画面缺失。
- 输出合成后的 AVFrame。

主要技术：

- libavfilter
- buffer
- buffersink
- scale
- overlay
- xstack
- fps
- format

### 4.5 AudioMixer

职责：

- PCM 数据处理。
- 采样率转换。
- 采样格式转换。
- 声道布局转换。
- 多路音频时间对齐。
- 多路音频混音。
- 音量调节。
- 静音控制。
- 削波保护。

优先使用 libswresample 和 libavfilter 实现基础版本。

对于多路混音可研究 amix 等 FFmpeg 音频滤镜。

### 4.6 AVSynchronizer

职责：

- 统一时间基。
- 转换 PTS/DTS。
- 处理不同源的时间戳起点。
- 处理音视频同步。
- 处理视频帧迟到。
- 处理重复帧和丢帧。
- 处理音频连续性。
- 记录同步误差。

重点 API：

- `av_rescale_q`
- `av_compare_ts`
- `av_gettime_relative`

注意：

不同输入设备和协议的时间戳可能没有共同的时钟基准，必须通过输入时间轴归一化与同步策略处理，不能直接比较来自不同输入源的原始 PTS。

### 4.7 MediaEncoder

职责：

- H.264 编码。
- AAC 编码。
- 编码器初始化。
- 编码码率设置。
- GOP 设置。
- 帧率设置。
- 编码缓冲控制。
- 处理编码器 flush。
- 输出编码后的 AVPacket。

重点 API：

- `avcodec_find_encoder`
- `avcodec_alloc_context3`
- `avcodec_open2`
- `avcodec_send_frame`
- `avcodec_receive_packet`

### 4.8 StreamOutput

职责：

- 创建输出 AVFormatContext。
- 创建输出 AVStream。
- 复制或设置编解码参数。
- 写入媒体头。
- 写入 AVPacket。
- 维护输出时间戳。
- 处理网络错误。
- 安全停止输出。
- 释放输出资源。

重点 API：

- `avformat_alloc_output_context2`
- `avformat_new_stream`
- `avcodec_parameters_from_context`
- `avio_open2`
- `avformat_write_header`
- `av_interleaved_write_frame`
- `av_write_trailer`

### 4.9 StreamManager

职责：

- 管理输入媒体源。
- 管理解码器和编码器。
- 管理处理线程。
- 管理输出状态。
- 协调启动和停止。
- 处理异常传播。
- 统计运行指标。
- 管理整个媒体处理 Pipeline 的生命周期。

## 七、CMake 构建要求

### 7.1 编译标准

必须强制使用 C++11：

```cmake
set(CMAKE_CXX_STANDARD 11)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
```

### 7.2 FFmpeg 依赖

优先使用 CMake 的 PkgConfig 模块：

```cmake
find_package(PkgConfig REQUIRED)

pkg_check_modules(
    FFMPEG REQUIRED IMPORTED_TARGET
    libavformat
    libavcodec
    libavutil
    libavfilter
    libswresample
    libswscale
)
```

通过 `PkgConfig::FFMPEG` 目标链接依赖库。

### 7.3 编译命令

Debug：

```bash
cmake -S . -B build/debug -DCMAKE_BUILD_TYPE=Debug
cmake --build build/debug -j$(nproc)
```

Release：

```bash
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release
cmake --build build/release -j$(nproc)
```

测试：

```bash
ctest --test-dir build/debug --output-on-failure
```

### 7.4 编译选项

启用：

- `-Wall`
- `-Wextra`
- `-Wpedantic`

Debug 模式确保有调试符号。

Release 模式使用合理的优化等级。

线程库使用 CMake `Threads::Threads` 目标链接。

禁止将所有源文件无条件写入单一庞大的 CMake 配置，应随着模块规模增长合理拆分 Target。

## 八、代码质量规范

1. 严格使用 C++11。
2. 优先通过 RAII 管理资源。
3. FFmpeg 资源必须正确释放。
4. 不允许内存泄漏。
5. 不允许无限增长队列。
6. 所有线程必须具备安全退出机制。
7. 跨线程访问必须遵守同步规则。
8. 不能使用 detach 逃避线程生命周期管理。
9. 不能在错误处理时无条件终止整个进程。
10. 所有关键异常必须记录日志。
11. 所有时间戳转换必须标明 time_base。
12. 必须正确处理编码器、解码器 flush。
13. 不得混淆 AVPacket 和 AVFrame 的资源所有权。
14. 必须正确处理 EAGAIN 和 EOF。
15. 不得使用不兼容的封装格式直接写出。
16. 不得依靠硬编码本机文件路径运行。
17. 不得将未实现功能标记为完成。
18. 优先实现简单、清晰、可维护的代码，不进行过度设计。

- 高级 Linux/C++ 工程师
- FFmpeg 音视频研发工程师
- 系统架构设计助手
- 代码审查助手
- 音视频技术导师

开发规则：

**1. 一次只开发一个 Phase。**

不得未经许可直接开发多个阶段。

**2. 开始编码前解释技术方案。**

说明本阶段涉及的关键 FFmpeg API、数据流、时间基和资源管理。

**3. 每完成一个功能必须编译验证。**

不可在未编译的情况下宣称代码可运行。

**4. 必须进行真实测试。**

测试受环境限制时，应明确列出未完成的验证项目。

**5. 每阶段完成后更新文档。**

包括开发进度、学习笔记、运行方法和测试结果。

**6. 不得擅自引入新的大型依赖。**

优先使用 C++11 标准库和 FFmpeg。

**7. 不得擅自修改项目技术路线。**

当前不部署 SRS，不实现 WebRTC。

**8. Git 提交前展示变更。**

仅在收到明确授权后执行 Git commit。

**9. 不允许伪代码冒充实现。**

所有完成的功能必须有实际代码和测试方法。

**10. 以学习和工程质量为目标。**

不要为了快速完成而牺牲资源安全、线程安全、时间戳正确性和代码可维护性。
